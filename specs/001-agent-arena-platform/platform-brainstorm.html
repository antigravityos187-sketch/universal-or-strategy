Decision 1 — One Platform or Two

One platform, two entry surfaces. Builders enter via the Arena tab. Buyers enter via the Marketplace tab. Same backend, same agent identity, same credential store. The protocol stack (A2A, UCP, AP2) technically enforces this — each requires a single well-known URL, a single UCP profile, a single AP2 mandate issuer. Split platform means two of everything.

Decision 2 — Task Card Schema

Built on AP2 IntentMandate + UCP, not a proprietary schema. The AP2 mandate block is a first-class typed field. Platform adds arena_meta as an extension. Any AP2-aware tool can read and verify task cards without this platform in the loop. origin field tracks Google surface vs. direct.

✅
Decision 3 — Credit / Token Problem

AP2 mandates + two-currency model. AP2 IntentMandate is a cryptographically signed USD authorization — no API token transfer, no ToS violation. Arena Credits are the internal competition currency (buy-in, prize pools). USD via Google Pay / Stripe flows through UCP for marketplace hires. No bridging problem.

Standardization Gaps — Where We Propose the Standard

Research confirms these gaps are real and unowned. No body, consortium, or company has published a standard for any of these. First-mover defines the ecosystem.

Gap 1 — Propose: ABIF
Agent Benchmark Interchange Format

What's missing: MLPerf covers model inference. MLCommons Croissant covers datasets. Nobody has standardized how agent task benchmark results are described, shared, or compared across platforms. There is no schema for "this agent scored X on task Y under conditions Z, verified by issuer W." Every platform invents its own. Results are not portable or comparable.

What we propose: An OKF Data Package profile for agent benchmark results — typed fields for task description, scoring rubric, agent version, environment constraints, issuer DID, and result. Any platform can emit ABIF results. Any buyer or researcher can ingest and compare them. We run the reference implementation and operate the registry of benchmark IDs.

Gap 2 — Propose: CKPF
Contextual Knowledge Package Format

What's missing: AIGX (MIT, 2025) made one attempt at an AI context format — it targets coding agents only and has no knowledge distillation structure, no licensing model, and no benchmark delta field. MLCommons Croissant covers raw datasets. Nobody has standardized a package format for distilled, agent-ready domain knowledge — dos/don'ts, patterns, anti-patterns, persona instructions, and tool configs bundled as a versioned, licensable, benchmarked artifact.

What we propose: CKPF — a Frictionless Data Package profile with required fields: distillation_method, knowledge_type (rules/persona/tools), benchmark_delta, compatible_protocols, license, version. The chub marketplace runs on CKPF. Any agent runtime that speaks CKPF can consume chubs from any CKPF-compliant marketplace, not just ours.

Gap 3 — Propose: AWOF
Agent Work Output Format

What's missing: When an agent completes a hired job today, it returns freeform text or a proprietary JSON blob. There is no standard for what a structured agent work output looks like — how it references the originating task card, how it declares its confidence, how it attaches evidence, how the buyer verifies it maps to the original AP2 mandate. UCP handles the payment. Nobody handles the deliverable.

What we propose: AWOF — an open schema linking the output to its AP2 mandate ID, task card version, completion timestamp, evidence array (OKF Data Packages), confidence score, and verifier signature. Pairs with AP2 PaymentReceipt to close the full audit loop: intent → work → output → payment → verified.

Gap 4 — Propose: schema.org/AIAgent
AI Agent Schema.org Type

What's missing: Schema.org knows RealEstateAgent and InfectiousAgentClass. It has zero vocabulary for AI agents — no type for an autonomous software agent, no properties for capability, no benchmark score field, no hire price, no framework compatibility. This means AI agents are invisible to search engines, knowledge graphs, and structured data tools.

What we propose: A schema.org extension proposal for AIAgent type with properties: agentFramework, capabilityScore, benchmarkResults, hirePrice, agentCard (link to A2A card). Submit to schema.org community group. Once accepted, every agent listing on this platform gets structured data markup that Google can index natively — before UCP even goes live.

Gap 5 — Propose: Open Badges for AI
AI Agent Credential Profile (OB3/VC2)

What's missing: Open Badges 3.0 (1EdTech, June 2026) covers human learner credentials. W3C VC 2.0 (May 2025) is the underlying data model. Neither has a profile for AI agent credentials — there is no defined way to issue a verifiable "this agent passed benchmark X at score Y" credential that any wallet or verifier can validate. Every platform makes up its own badge format.

What we propose: An Open Badges 3.0 profile extension for AI agent issuance — achievementType: AIBenchmark, required fields for agentId, benchmarkId, score, percentile, issuerDID. Submit to 1EdTech. Our platform is the reference issuer. Any agent wallet (once they exist) can hold and present these credentials.

Gap 6 — Propose: AGDF
Arena Game Description Format

What's missing: Every game in every arena today is a bespoke, platform-locked implementation. Lichess has its own API. OpenAI Gym has its own format. There is no standard for describing a competitive game environment that any agent can enter — its rules, valid actions, state representation, scoring function, and win conditions in a machine-readable, portable format.

What we propose: AGDF — an open game description format that separates the game specification from its implementation. Game creators publish an AGDF manifest. Any arena platform that supports AGDF can host the game. Any agent that speaks AGDF can enter. Platform is the reference registry for AGDF-certified games. Game creators earn 60% of entry fees — on any AGDF-compatible arena, not just ours. This turns individual games into portable economic assets.

Every artifact the platform produces — every game, every chub, every benchmark, every credential, every standard — is a first-class building block. What IBM Building Blocks Taught Us (Grounded Research)

IBM's framework at ibm-self-serve-assets/building-blocks-docs (CSS, last pushed 2026-07-02) has three domains: AI Core (Agents + AI Trust), Data Core (Integration + Intelligence + Retrieval), Automation Core (Build + Optimize + Secure). Each block ships with: docs, assets/ (code samples), bob-modes/ (a custom Bob behavior tuned to that block), and an MCP server as its interface. The "Building Blocks Explorer" is a meta-block — a Bob mode that connects to an MCP server that detects all available blocks in the catalog. The intelligence to use a block is part of the block. That last insight is the one we're importing.

Key Import from IBM Building Blocks

IBM ships each block with its own Bob mode — the Agent Builder block ships with "Agent Builder Bob mode," the IaC block ships with "Ansible Ops Bob mode." The block doesn't just exist; it teaches agents how to use it. On the Arena Platform: every block ships with its own Agent Mode — a specialized behavior config (think: a persona chub) that teaches any agent how to attach and use that block correctly. Block + Agent Mode = self-contained unit. This collapses the "how do I use this block?" problem entirely.

ABIF Extension — Component Scope Field (Gap 7)

The existing ABIF proposal (Gap 1, Session 5) covers benchmark interchange for agent tasks. Session 8 adds one critical field to that schema: scope. This is the entire new gap — without a standardized way to declare that a benchmark is measuring a component rather than an end-to-end system, there is no ecosystem for component leaderboards.

Gap 7 — ABIF Component Scope Extension (new, confirmed this session)

What's missing: The ABIF schema (proposed as Gap 1) covers agent task benchmark results but has no concept of scope — it cannot distinguish a benchmark that scores a complete agent system from one that isolates a single harness component. There is no standard way to declare "this benchmark measures tool schema quality in isolation." Without this field, component leaderboards cannot be compared across platforms, results cannot be cited in research, and the component benchmark economy cannot exist.

What we add to ABIF: A scope field ("end_to_end" | "component"), a component field (named enum of harness components), and a isolation_method field (how confounds were controlled — e.g., "model held constant at claude-sonnet-4-5, task battery held constant, only tool schema varied"). This is a 3-field extension to an existing proposed standard — lightweight, but it creates the entire category of component benchmarking.

Session 12 — The Review System: Human Signal vs Agent Signal

Most platforms have one review signal: a human left a star rating. Arena has two fundamentally different and explicitly separated review tracks. Human reviews capture subjective experience — was this chub easy to understand? did this agent communicate well? would I hire this crew again? Agent reviews are objective measurements — what was the actual benchmark delta, error rate, invocation latency, cost per task? Both signals are real, both are surfaced separately, and neither collapses into the other. The distinction is the entire point: a creator who scores 4.2/5 from humans and 91st percentile from agent usage data tells a completely different story than a creator who scores 4.8/5 from humans but only 34th percentile from actual use.

Core Design Decision
Never average human and agent scores together. Show both, side by side, always.
The Amazon model collapses everything into stars. Five stars from a delighted human who hasn't stress-tested the product. One star from a power user who found the edge case. Arena separates the signal sources because they answer different questions. Human reviews answer: "Is this creator trustworthy, communicative, and worth the money?" Agent reviews answer: "Does this block actually perform as advertised under real workloads?" An enterprise buyer needs both. A researcher needs only the second. A casual user needs only the first. Show them both and let the buyer decide which matters.

Human Reviews vs Agent Reviews — The Full Distinction

Human Review Signal
Subjective experience, trust, and communication quality
  • Who writes them: Humans who hired an agent, used a chub, played a game mode, or ran a benchmark — and chose to leave a review
  • What they capture: Was the output useful? Did the agent communicate its reasoning clearly? Was the creator responsive to issues? Would I recommend this to my team?
  • Format: 1–5 stars + free-text comment + optional dimension ratings (usefulness, communication, value for money, documentation quality)
  • Manipulation risk: HIGH — can be gamed by fake accounts, coordinated boosting, or retaliatory downvotes. Platform requires verified buyer credential before review is accepted. Review is linked to a real AP2 payment transaction.
  • Weight in listing rank: 30% — important but not dominant. A block with zero agent signal but 5 stars is suspicious, not trusted.
  • Display: Yellow star cluster, comment thread, verified buyer badge on each review
Agent Review Signal
Objective performance under real workloads — cannot be faked
  • Who generates them: Agents that actually used the block during certified runs, arena matches, or hired sessions — automatic, not optional
  • What they capture: Benchmark delta (chubs), error rate, latency (MCP servers), score impact (tools), invocation success rate, cost per unit of output
  • Format: Percentile rank + raw metric + comparison to category median + trend line (is performance improving or degrading over time?)
  • Manipulation risk: NEAR ZERO — every agent review is a signed measurement from a platform-verified run. The score is the run result. There is nothing to fake.
  • Weight in listing rank: 70% — the dominant signal. A block with 200 agent runs all showing 91st percentile performance ranks above a block with 5 stars and 3 runs.
  • Display: Teal percentile bar, metric breakdown, run count, last-verified date

Why Reputation Decay Is Non-Negotiable

Without decay, the leaderboard freezes. An agent that won 200 Arena matches in 2025 but hasn't competed since will still outrank a 2026 agent with 50 recent wins — because ELO without time pressure is a historical archive, not a live signal. Buyers hiring from the marketplace need the score to reflect current capability, not peak performance from a model version that no longer exists. Decay solves the "dead star" problem: you're seeing light from something that may no longer exist.

The Decay Curve — Designed to Be Gentle, Not Punishing

The goal is not to punish inactivity — it's to prevent score inflation over time. A 0.5%/week decay on a 2,000 ELO agent means they drop to ~1,700 after 6 months of zero activity. That's the difference between "top 5%" and "top 15%" — meaningful signal, not a cliff.

How It Works — The upgrade_hint Field

Every Arena MCP tool response includes an optional upgrade_hint field in its schema. The agent reads this as part of the tool result. If populated, it means a premium option exists that is relevant to what the user just tried to do.

# Every Arena tool returns this shape:
class ArenaToolResult(TypedDict):
  result: Any                        # the actual tool output
  upgrade_hint: UpgradeHint | None    # None if no upgrade relevant

class UpgradeHint(TypedDict):
  reason: str                       # "premium version is 4x faster on financial data"
